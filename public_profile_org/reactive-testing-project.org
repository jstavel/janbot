# Reactive Testing — Spec-First testware, TypeScript proof against Kraken Pro

A TypeScript monorepo that implements Spec-First testing as an executable
architecture against the Kraken Pro trading UI (read-only critical path).
149 commits, 50 specification documents, 4 completed epics.

Use when demonstrating: Spec-First implemented, not just described; AI-assisted
development at scale; evidence-first verification pipeline; mature proof-of-work.

* What it is

The project proves a simple claim: describe the application **once** as a formal
model (FSM + contracts + Zod schemas). A deterministic orchestrator records
evidence (a corpus) from a live browser session. Pure validators verify that
evidence **offline** — no browser needed — and failures surface as reviewable
Gherkin for a human to adjudicate. One navigation funds N validations. **The
model is the single source of truth**; every test script, plan, and corpus is a
derived byproduct.

* Architecture (as built)

The pipeline has two deliberately separated phases:

**Phase 1 — Authoring** (offline, AI-assisted, human-reviewed):
Gherkin features in `features/` are distilled into the executable model
(`model/fsm.ts` + `model/contracts.ts` + `model/schemas.ts`) — the SSOT.
A named test plan is derived from the model.

**Phase 2 — Execution & verification** (deterministic, no AI in the loop):
The orchestrator runs the plan against the live app via Chrome DevTools
Protocol (CDP), collectors write raw evidence into `corpus/`, then pure
validators re-check that evidence offline. A failure surfaces as reviewable
Gherkin; a human adjudicates *spec drift vs app bug*.

Key architectural decisions visible in the code:

- **Model = SSOT.** Three files hold the entire truth about the application.
  Everything else is derived. `model-version.ts` hashes the three files (SHA-256);
  the orchestrator refuses a stale plan. A CI test (`model-version.test.ts`)
  catches a forgotten plan regeneration.
- **Repro scripts generated from the model.** The `repro/repro-generator.ts`
  emits standalone scripts that a developer runs without the test framework —
  just Playwright + model + action-map. No orchestrator, no validators, no
  collectors. This means a developer can reproduce a bug path *without*
  learning or installing the testware. The emitted script imports the live
  action-map, so a regenerated repro always reflects the current spec
  (FR-12a, AD-7). An unmodeled path is reported as a gap — never silently
  approximated (FR-12c).
- **Action map outside the model.** Concrete Playwright locators live in
  `orchestrator/action-map.ts`, outside the model hash. Editing a locator never
  bumps the model version.
- **Collectors write plain data.** Snapshot, probe, network, screenshot — all
  write plain JSON/files into the corpus. Never into TypeScript.
- **Validators are pure functions.** Corpus in → `ValidationResult` out. No
  browser, no network. Can run against any recorded corpus, any time.
- **One run funds N validations (AD-18).** A validator written months later runs
  against an *already recorded* corpus without a fresh browser session.
- **Layer/import discipline.** `collectors/`, `validators/`, and `reporter/`
  import no other project layer — only `model/` types/schemas (plus libraries).
  Only `orchestrator/` and `collectors/` touch a live `Page`.

* How it was built

The project was built using the **BMad method** — AI agents drive stories from
spec through implementation to review. All four epics (21 stories) were built
this way, each with:
- A specification document (`spec-*.md` in `_bmad-output/`)
- A SPEC.md with stories (`stories.yaml`)
- AI-driven implementation and tests
- A retrospective after each epic

50 specification documents exist in the implementation artifacts archive,
documenting every architectural decision from `spec-1-1-scaffold-the-executable-model`
to `spec-user-documentation-set`.

In the authoring phase, the AI agent uses Playwright MCP to explore the target
UI and propose a Gherkin feature file. The human's job shifts from *writing
code* to *deciding what is true* — reviewing AI proposals, catching
hallucinations, and ensuring the model stays accurate. The tool that drives
*verification* is the same one used for *authoring*; only the phase differs.

This is Spec-First applied recursively: the framework was *built* the same way
it *works* — specify first, then implement, then verify.

* Weaknesses this reveals

- **Adoption gap.** Like the 2019 origin, the idea is validated but not adopted
  outside the creator's domain. Without organizational change management and
  visibility, it stays at the individual-contributor level. Related object:
  `reactive-testing-origin` (same weakness, 6 years apart).
- **Proof-of-concept scope.** The model covers only the Kraken Pro read-only
  critical path. Non-read-only flows (trading, settings) are not modelled.
  No headless mode exists — recording always requires an authenticated browser.
- **Single application.** Validated against one UI (Kraken Pro). The architecture
  is generic, but no second application exists to prove portability.
- **No CI-format output.** Reporters write Gherkin + JSON into the corpus folder;
  no xunit/JUnit output exists for integration with standard CI dashboards.
