# A key with no expiry is a permanent grant — rotation policy for agent-held secrets

Use when asked how credentials are handled for an AI service, or how the
"agent has access to my key" problem can be bounded.

* The rule this is an instance of

A control whose parameters disagree with each other does not protect anything; it
becomes a **scheduled failure**:

- a validity shorter than the interval at which the credential is actually refreshed,
- a quota computed for a calendar period while the thing it bounds lives per key,
- a cap that resets when the credential rotates — restoring the allowance exactly
  when the old copy is still usable.

The rule: **fix each parameter against the object it really bounds** (the lifetime of
one credential, not the month; the rotation interval that really happens, not the one
that is intended) and **state the control's own failure mode out loud** — when it
fires, is it an outage, a silent stop, or a bill?

The worked example below is an API key held by an agent. The rule is not about keys,
which is why this object sits under way-of-working rather than security.

* The threat, stated precisely

An agent talks to a model provider on the owner's behalf, so it necessarily
holds the provider API key. The risk is not in the call itself — it is that the
agent can **write the key somewhere and keep it**:

> *"If it stores the key without my knowledge, then it has it forever."*

No amount of prompting fixes this, because the persistence is outside the
prompt. The threat model is therefore not "the key leaks to an attacker" but
**"the key survives the task"** — a grant with no end date.

* The countermeasure — three properties, one store

| Property | Purpose |
|----------|---------|
| Short expiry | bounds the damage window; every key becomes useless on its own |
| Usage caps (rate and pricing ceiling) | bounds the blast radius while the key is valid |
| Regular rotation | shrinks the window in which a persisted copy is still useful |

And a single authoritative place to do it:

- **Google Cloud Secret Manager as the only store** — auditable access,
  versioning, and a real revoke path. Not `.env`, not a config file, not a
  conversation.

The key is obtained **ephemerally at runtime** (in memory), never written to
disk, logs or a user-visible context.

* Sizing the cap — per key, not per account

The limit is set on a **key**, not on the account, so rotation resets it: four
rotations a month mean four independent allowances, and the real monthly exposure
is four times the cap, not the cap. Sizing therefore has to be computed against
the **lifetime of one key**, never against a month.

| Figure | Value |
|--------|-------|
| legitimate spend for one key's lifetime | *S* |
| cap in force | **≈ 1.5 × S** |
| hard stop if the rotation lapses | ≈ 1.5 × the lifetime — about ten days of maximum spending |
| worst case per month (*k* keys, each abused to its cap) | *k* × cap — with weekly rotation, ≈ 1.5 × the legitimate monthly spend |

The last row is the part worth remembering: **the exposure multiplier equals the
cap's margin.** Set the cap at 1.5 × one lifetime and a month of fully abused keys
costs 1.5 × the legitimate month — the headroom allowed for safety is also the factor
by which a leak can exceed normal spend.

The reset period is deliberately **off**. A weekly reset would restore the
allowance and remove the hard stop: a key surviving a missed rotation would keep
spending. Without reset, the cap doubles as a **rotation-lapse detector** — the
key dies after about ten days of maximum spending, which is a visible failure
rather than a silent drain.

The price of that choice: a cap that has been reached looks like a broken key,
not like an exhausted budget. Hence the operational rule — **a 402/403 from the
provider means check the key limit, not the network.**

* Daily or weekly — the interval is a function of maturity

The interval is not a taste question; it is a trade-off between exposure and
operational cost:

- **Daily** minimises the exposure window and is preferred *once rotation is
  fully automated and monitored*.
- **Weekly** is the sane starting point while rotation still costs a human
  action — a daily manual rotation is not a policy, it is a future outage.

So the policy is a **transition**: weekly first, daily once the rotator runs
unattended with canary rollout and rollback. "Daily" without automation is
security theatre; the automation is the actual control.
