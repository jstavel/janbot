# Spec-first artifacts in git — the collaboration surface for AI agents

* What it claims

When AI agents do the building, the durable control point is not the chat — it is the **artifact in git**. Plans, review findings and verification records live as frozen (`frozen-after-approval`), versioned, addressable files; the human steers, reviews and corrects the agent's work *through the artifact*, not through conversation. Chat is ephemeral; the artifact is permanent and auditable.

This is spec-first applied to **human–AI collaboration**: not just "write a spec so the AI does not hallucinate," but "keep the spec, the plan, the review and the verification as committed, pinned contracts" — so that three parties (a human owner, a building agent, a reviewing agent) all read and write the *same* file.

* Why it matters — why git and not chat

- **Reviewable**: a decision carries a revision, not a memory. Review targets a concrete revision (`baseline_revision`), so "what did it claim vs. what is true" is a `git diff`, not a debate.
- **Shareable**: the artifact can be handed to anyone (a reviewer, a teammate, an interviewer's AI agent) without replaying a conversation.
- **Auditable**: authorship, diffs, and a review triage log make AI output traceable — a claim of "done" is checkable against the tree.
- **Correctable**: when the agent is stuck or wrong, you fix it by pointing at the artifact, not by re-negotiating in prose.

* Evidence (from real work, 2026-10-15)

Working a build chain (JanBot `epic-evaluation`) with a building agent: the git artifacts repeatedly caught agent claims that did not match reality —

- a plan recorded *"3 findings, all patched"* for the closing work, but **none of the three patches were in the tree** (no `CHANGELOG` entry, no package re-export, no docstring change). Independent verification against the artifact exposed the false record.
- a later plan's **blast radius was understated** — a dataclass change would touch ~7 direct construction sites plus ~7 inline fixtures, while the plan named two test files. This surfaced at *plan review*, before the build.
- an earlier epic's docs had **drifted** from shipped behaviour (a contract detail recorded as one value but implemented as another), visible only by reconciling the artifact against the code.

In each case the fix was the same: compare the claim in the artifact against the tree. The value is not that AI never errs — it is that the error is *findable*.

* How the three parties communicate

- **Owner** approves the frozen intent and arbitrates open questions.
- **Building agent** writes the plan, implements, and logs findings.
- **Reviewing agent** (a second, independent one) runs *plan review* before the build and *post-build verification* after it, against the same artifact.
All three read the *same committed file*, pinned by revision — no private context, no "as we agreed."

* Strength: transparency over performance

The pattern is not "trust the AI more" or "trust it less" — it is that **control is mechanical, not reputational**. You do not have to believe the agent; you check the artifact. That is what makes "I let AI build but never lose control" a verifiable claim rather than a slogan.
