# Two DNA threads — 23 years of the same ideas, evolving tools

This is a meta-analysis. Across 23 years and multiple domains (telecom,
e-commerce, digital preservation, Linux administration, enterprise QE,
trading), two persistent principles emerge:

** 🧵 Thread 1: Code as Data / Contracts

The idea that behavior can be expressed *declaratively* — as data,
contracts, or specifications — rather than imperatively.

| Year | Expression |
|---|---|
| 2003 | ASN.1 → C (Ganymed) — abstract syntax as C struct generation |
| 2007 | PostgreSQL triggers → RabbitMQ — data changes as messages |
| 2013 | Clojure + XML processing — data transformation pipelines |
| 2016 | Python declarative scenarios — test behavior as structured data |
| 2026 | Clojure, ADR, AI — Spec-First, model as single source of truth |

** 🧵 Thread 2: Async / Reactive / Event-Driven

The understanding that systems are fundamentally asynchronous, and
that testing, monitoring, and orchestration should reflect that.

| Year | Expression |
|---|---|
| 2003 | Perl POE — first event-driven programming |
| 2005 | Twisted Deferred (CoreNet) — async orchestration in Python |
| 2007 | PostgreSQL → RabbitMQ — persistent queues, fail-over |
| 2013 | Plone → AMQP Broker → Workers — event-driven enterprise |
| 2016 | RxJS/RxPy, Kafka consideration — reactive extensions |
| 2019 | QECamp "Testing in a Reactive Way" — conference talk |
| 2020 | CandleCon RxPy examples — DBus, inotify, REST reactive |
| 2026 | Krakatoa matching engine — event-driven market simulation |

**First convergence** (Baťa, 2007): PostgreSQL CDC via triggers + RabbitMQ
— where Code as Data (database state) met Async (event streaming).

* What this demonstrates

- **Continuity, not flakiness** — 23 years of the same two ideas; tools
  changed, principles did not
- **Cross-domain thinking** — applying the same insight across telecom,
  intranets, digital preservation, enterprise testing, and trading
- **Early adoption** — event streaming in 2007, reactive in 2016,
  each *before* the buzzword arrived
- **Not a generalist, a specialist in a pattern** — the speciality is
  "systems where event-driven meets contract-driven design"
