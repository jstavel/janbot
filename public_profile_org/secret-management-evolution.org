# Secret management — from git-crypt to short-lived workload identities

Use when asked "how do you handle credentials?" The answer is not a list of
tools; it is a line of evolution in which the question changes from *where do I
store the secret* to *can I avoid having one*.

* The arc

| Era | Mechanism | Root of trust | The cost that taught the next step |
|-----|-----------|---------------|-------------------------------------|
| Config files | values in config files, copied by hand, never committed | nothing | a secret in a file someone can read |
| `.env` (12-factor) | everything through environment variables | the shell / the deploy script | the secret sits in the process environment |
| `.env` encrypted in git | **git-crypt** | a human with a GPG key | the secret lives in git history; only rotation removes it, and code review is blind to it |
| **Ansible Vault** | encrypted variable files, password typed at every run | a human at a prompt | deliberately *not automatable* — so a deploy always needed a human |
| **HashiCorp Vault** | external store, leases, static and dynamic secrets | an authenticated identity | the app still had to hold a token |
| Personal credentials | **Bitwarden** with 2FA; hardware key on admin accounts | a physical second factor | manual, but nothing long-lived on disk |
| **JanBot (now)** | Secret Manager + IAM + service accounts; short-lived token issued from a 2FA-protected owner account, impersonating a service account | the identity of the task | — |

The direction is consistent: **each step moves the root of trust from a file,
to a human, to an authenticated identity.**

* Honest framing — where I actually am on this map

This distinction matters more than the tool list, and it is stated plainly:

- **Encrypted secrets in a repo and an external secret store** — years of
  practice. git-crypt, Ansible Vault and Vault were used in real delivery,
  not read about.
- **Workload identity / short-lived credentials** — *being built now*, in
  JanBot, and therefore verifiable in the repo rather than in an interview
  claim. The concepts come from the Vault years (static vs dynamic secrets,
  leases); what is new is the **cloud mechanics**: IAM bindings, secret
  versioning, key providers, and the difference between mounting a secret and
  injecting it as an environment variable.
- **Still learning** — the shape of a complete policy: which role may do what,
  how a token is scoped to a single piece of work, and how to verify that an
  agent never receives more than it needs.

* The rule I now design towards

The rule in one line: **the best secret is no secret** — explained in the next
section, because the phrase is only useful when it is precise.

- **No long-lived credentials in an agent's environment.** The agent gets a
  short-lived token obtained through a 2FA-protected account and impersonating
  a service account; when the work ends, the credential ceases to exist.
- **Service account + roles, not personal credentials.** Roles are defined by
  the *type of work*, not by convenience — the point is partly least privilege
  and partly **accident prevention**: a deploy role must not be able to trigger
  an unwanted redeploy.
- **Secrets out of dotfiles.** All credentials and tokens move out of shell
  startup files into a 2FA-protected vault.
- A static service-account key file is treated as an anti-pattern, not as the
  default.

* What "the best secret is no secret" actually means

The phrase sounds like a paradox. It is a literal instruction, and it is
precise about *which* secret disappears.

**The claim.** Every secret-using system has a *root of trust* — something
everyone assumes stays secret. The question is not whether secrets exist, but
**where that root sits**. The goal is to move it until, from the application's
point of view, **no long-lived credential exists at all**: there is nothing to
lose because there is nothing to steal.

**The mechanism — the application holds an identity, not a key.** The
application proves *what it is and where it runs* (the platform already knows:
this container, this project, this deploy), and exchanges that fact for a
short-lived credential through workload identity federation / OIDC. The token
lives for minutes, is scoped to a single permission ("apply to this stack", not
"do anything"), is used, and expires. No state remains; next time the whole
exchange happens again from zero.

The exercise stated positively: **the root of trust is the identity of the task,
not the key it carries.**

**Why it is stronger, not merely cleaner.**

- **Nothing to rotate.** A credential that never exists cannot leak, so there is
  no rotation event and no "we will rotate after the incident".
- **A stolen token is nearly worthless**: minutes of life and one narrow scope,
  against a static key that is useful for years.
- **No secret in git history, in the image, or in the environment** — the whole
  class of problems the earlier eras fought with.
- **Auditable by construction**: every task obtained its token under its own
  identity, so it is visible *what* accessed *what*, and when.

**What it does not mean** (the part that makes the claim defensible).

- It does **not** mean "no authentication" or "no secret store anywhere". A
  managed store (Secret Manager, Vault) still exists; what disappears is the
  **long-lived credential in the application's hands**.
- It is **not always achievable**. Where the platform cannot issue an identity —
  a third party that no OIDC supports, a legacy system that only understands
  static access — a real secret is unavoidable.
- Hence the exact formulation used: **avoid creating a secret wherever the
  platform can issue an identity; where it cannot, keep the secret in a managed
  store and still give the workload only a short-lived token.**

**What makes it concrete rather than aspirational.** In JanBot this is the E1.5
junction: Cloud Run referencing the image by digest, secrets in Secret Manager
behind IAM, and an agent receiving an impersonated short-lived token instead of
a key file. Until that exists the claim is direction, not evidence — which is
exactly why the honest framing above separates "years of practice" from "being
built now".

* Open question, recorded live

Do temporary identities exist outside the cloud? Google's short-lived
credentials are the reference model; whether Linux offers an equivalent
native mechanism for system-level access is an open research question, not a
claim. It is recorded here because the honest state of a question is also
evidence about how the person works.
