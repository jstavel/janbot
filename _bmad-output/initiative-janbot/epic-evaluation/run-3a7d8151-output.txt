raw-answer: How do you handle credentials and secrets? — The approach to handling credentials and secrets has evolved from storing encrypted secrets in a repository and using external secret stores to focusing on short-lived workload identities. The current design principle is "the best secret is no secret," aiming to avoid long-lived credentials.

Key practices include:
*   **No long-lived credentials in an agent's environment**: Agents receive short-lived tokens obtained through a 2FA-protected account that impersonates a service account. These credentials cease to exist once the work is complete.
*   **Service accounts and roles**: Roles are defined by the type of work, not by convenience, to enforce least privilege and prevent accidents.
*   **Secrets out of dotfiles**: All credentials and tokens are moved from shell startup files into a 2FA-protected vault.
*   **Avoiding static service-account key files**: These are considered an anti-pattern.

The evolution of mechanisms includes:
*   **Encrypted secrets in a repo and an external secret store**: Tools like git-crypt, Ansible Vault, and HashiCorp Vault have been used.
*   **Workload identity / short-lived credentials**: This is an ongoing development, utilizing cloud mechanics such as IAM bindings, secret versioning, and key providers.
*   **Personal credentials**: Managed with tools like Bitwarden with 2FA and hardware keys for admin accounts.
*   **Current approach (JanBot)**: Involves Secret Manager, IAM, and service accounts, issuing short-lived tokens from a 2FA-protected owner account impersonating a service account.

This progression consistently moves the root of trust from a file, to a human, and finally to an authenticated identity.
